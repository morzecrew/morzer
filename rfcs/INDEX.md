# RFCs

Design proposals for morzer. Each RFC captures a design before or while it is
built: the problem, the state of the code today, the locked decisions with
their rationale, and what is deliberately excluded.

## Allocating a number

The next free number is **0019**. Before creating an RFC, glance at the table
below (or `ls` this directory) and take the next unused integer — numbers
collide when minted in parallel. Update this table in the same change.

Filename: `NNNN-kebab-title.md`. Keep the `# RFC NNNN — Title` H1 and the
number in the filename in sync.

| [0008](0008-test-coverage-program.md) | Testing the claims: a coverage programme to 95% | ✅ Complete | Raises coverage from a measured 70% to 95%, and makes every advertised security property name the test that enforces it. Written after measuring that `go test` alone reports 59.5% while the union with a `-cover`-instrumented acceptance run is 70% — ten points of real testing were invisible, so every judgement about where to test next was made against the wrong map. Of the remaining gap, 29% is I/O error branches and 71% is reachable behaviour, 604 statements of it whole CLI commands nothing drives. The motivating find: `redactAttr`, the enforcement point for "secrets never reach a log", is 21% covered and its `WithAttrs` path 0% — and redacts eagerly, so a value captured before a secret is registered is written in the clear (demonstrated; not currently reachable, because the only two call sites happen to pass operation ids). Shipped 2026-08-04: all five phases complete as designed, union coverage 70.0% -> **81.6%**, an inventory of 50 claims each naming the test that fails without it, and the predicted defect found — the redaction handler claimed to scrub anything that stringifies while handling only `string` and `error`, so a `Stringer` or a struct printed its secret in full. The container suites answer what a fake cannot: `down` really preserves its volume, a `pg_dump` the manager took really restores, and `pg_isready` without `-h` reports the entrypoint's throwaway server as ready. **95% is not met** — §16 names the 1438 statements that stand between here and it, and §17 plans P6–P11 against them. The gap is breadth, not depth: 1438 statements in 1225 blocks across 468 functions, only 55 of them in functions with twenty or more uncovered, so there is no large win left. Two new mechanisms carry it — huh's accessible mode to make the `init` wizard answerable without a pseudo-terminal, and a corrupt-archive builder for extraction's refusals — and everything else is fixtures against switches that already exist. P6–P11 then shipped: the `init` wizard is answerable without a pseudo-terminal through huh's accessible renderer, sops failures and hostile archives are driven one refusal at a time, and the operation steps are failed at the supervisor, the renderer and a read-only filesystem. **86.1%, and the target is not met** — 699 statements short, because the §17 estimates were roughly three times optimistic about statements that cluster behind one hard prerequisite. Two more claims-without-enforcement found on the way: `preflight.NoUnfinishedOperation` is documented and wired into nothing, and the scripted runner this programme added returned no `*ExitError`, so an adapter classifying a failure saw a success. Closed 2026-08-04 at 86.1% with the target revised rather than met (decision 13): the claims inventory is the deliverable and is finished, the percentage was always the proxy, and what remains is named in §19 rather than promised. |
| [0009](0009-backup-targets.md) | Backup targets: getting a backup off the machine | ✅ Complete | Adds a `BackupTarget` port and a scheme registry — `file://`, `ssh://`, `s3://` — so a backup lands somewhere the machine that took it cannot delete. Mirrors the release-source registry byte for byte rather than inventing a second shape. Every backup today is on the disk that will fail: the recovery documentation already tells operators to copy them off by hand, and the recovery test simulates it with a `copyTree` that this RFC lets it stop faking. Pushing happens after verification and before retention, and **a failed push fails the backup** — reporting success for data that is still only on the doomed machine is the thing this exists to prevent. The interesting problem is credentials: restoring from a bucket needs credentials that live in the state that is in the backup that is in the bucket, so the export carries them, flags override, and `file://` needs none. No dedup, no incremental, no restic — §8 records the measurement that would reopen that. Shipped 2026-08-04; §12 records ten dated amendments — a push-failure policy that would have deleted the very backup it was protecting, a host-key pin that failed against honest servers, a listing prefix that deleted a neighbouring backup, a pre-update backup that never left the machine, and six more found by auditing the shipped implementation, including a `--dry-run` that mutated and a second ssh target whose host key was never checked. |
| [0010](0010-compose-volume-capture.md) | Capturing Compose volumes | ✅ Complete | Lets a backup include the project's named volumes, so a release with no backup hook still produces something restorable when there is product data to capture -- bind mounts and excluded volumes do not count, and a release with neither a hook nor a capturable volume is refused rather than given an empty backup -- and a release with a database hook does not silently lose its uploads. The whole RFC hangs on one question: copying a live volume gives a *crash-consistent* copy, not an application-consistent one, so a volume copy of a running database is not a database backup and the design must not let anyone believe it is. **Decision 10 resolved in favour of cold-by-default**: the vendor writes `consistency: hot` where it is true or `exclude` where the hook owns the data, and an undeclared volume is captured with its services stopped — refined so only the services mounting that volume stop, all of them once, and `--no-downtime` *skips and reports* rather than downgrading to a hot copy. Shipped 2026-08-05 with all three phases: the manager's first image of its own (busybox, pinned, local-first, reported by `doctor`), a restore that replaces rather than merges and is refused by name while a mounting service runs, bind mounts reported and never captured, and a space check that refuses before anything is written or stopped. §12 records eleven ways the implementation changed the design — a staging bind mount that would have left root-owned plaintext uploads beside the encrypted backup, a space check that overflowed `int64` and turned its own refusal into a pass, and an error wrap that dropped the `docker pull` hint on the one machine where it mattered. |
| [0011](0011-bundled-container-images.md) | Bundled container images | ✅ Complete | Lets a release carry its own container images so installing it needs no credentials for the vendor's registry — the problem being credential distribution, not network isolation: ECR, Artifact Registry and ACR grant at IAM or project scope, so the smallest credential a vendor can issue is often far larger than intended. Per-image, so a release bundles its two private images and keeps pulling `postgres`. The converge path already accommodates this — `Pull` skips images that are present and `apply --startup` skips it entirely — so what is missing is only the getting-them-here part, and `doctor` already ships `runtime.images-local` warning about a condition with no supported remedy. **The obvious implementation does not work**: `docker save` writes `RepoTags: null` and no `RepoDigests`, so a loaded image never answers to the `name@sha256:…` the manifest pins and `HasImage` inspects — verified, and it is why the design is an OCI layout ingested through an ephemeral loopback registry (the acceptance harness has run one since 0005 for exactly this reason) with a digest-verified local index as fallback — both halves of which P2 then changed, below. Forging the daemon's own distribution metadata is recorded as rejected: it asserts provenance without checking it, which is the property 0005 found absent once already. Reverses 0004's "pulling container images … unchanged" non-goal and narrows its "the manager does not run a registry". **Design locked 2026-08-08**: a distribution mirror was weighed and rejected — practically available, and it still requires the customer to reach a registry, which for some of them is not true. The extraction ceiling rises via a budget declared in the manifest and read from the tar stream plus a free-space preflight, because extraction precedes verification and the signature cannot back that guard up. **P2 sent the design back on 2026-08-09, which is what P2 was for**: measured against a real daemon, a bundled image cannot answer to the reference its manifest pins — `docker image inspect` of the vendor's reference reports `No such image` after a loopback pull, because `RepoDigests` records only the name that was pulled, and `docker tag` answers `refusing to create a tag with a digest reference`, so nothing can put one there. The original spike inspected the loopback reference and was read as having inspected the vendor's. Decisions 18–21 replace it: the registry moves **into the manager's process** (the container form needed `registry:2` on a machine whose problem is that it cannot reach a registry), Compose receives a digest-derived alias `<repo>:morzer-sha256-<hex>` while `ref` stays the identity, an absent bundled image is a refusal rather than a pull — because a tag a registry could serve would let a digest-pinned deployment converge on unverified bytes — and the fallback ingest is withdrawn, its verification obligation discharged by the daemon's own V2 pull. **Complete 2026-08-09**: an acceptance run installs a hybrid bundle into a fresh root with the registry container removed and every local copy of the bundled image deleted, and converges — two containers running with no registry in existence. |
| [0012](0012-packing-images-into-a-bundle.md) | Packing images into a bundle | ✅ Complete | `morzer release pack` produces the bundles 0011 defines: copies every image the manifest marks `from: bundle` out of the vendor's registry into an OCI layout via `oras-go` — already a direct dependency, so no new supply-chain surface — and regenerates `SHA256SUMS` over the tree. Exists because the manual path scales badly in a specific way: the verifier fails closed on any unlisted file, an OCI layout is hundreds of content-addressed blobs, and `publishing.md` already prescribes a `find \| wc -l` cross-check as the workaround. Refuses fail-closed on a digest that does not match what the manifest pins (the check that makes provenance mean anything), on a stale `SHA256SUMS.minisig`, and on layout entries no manifest names. Signing, archiving and publishing stay out — signing keys are the boundary the manager does not cross — and the Non-goals exist because `pack` makes the manager *produce* an artefact for the first time, which invites "and sign them, and upload them". Gated on 0011 P1, and **design locked 2026-08-08** alongside it: writes in place, verifies the finished bundle by reusing `release verify` so a mismatch is caught on the vendor's machine rather than the customer's, and takes one `--platform` with per-image selection deferred. **The real-registry test deferred to 0011 P2 landed 2026-08-09**, and paying it off found that `pack` could not reach a loopback registry over plain HTTP — `oras-go` requires TLS where `docker pull` does not, so the promised parity with the ambient Docker configuration was false for exactly the throwaway registry a build machine uses. Loopback now matches Docker's rule; every other registry still requires TLS. |
| [0013](0013-bundle-authoring-experience.md) | Bundle authoring experience | 🚧 In progress | `release verify` — whose own help calls it "the command a bundle vendor runs in their own CI" — prints `bundle is valid` for a bundle whose template cannot render, demonstrated with an unterminated action and a reference to a field the render context does not have. It validates the manifest, checks referenced files *exist*, and never parses a template, so with `missingkey=error` doing its job the failure lands during an operator's `apply` instead. Makes parsing unconditional and puts rendering against a synthetic context behind `--render-check`, opt-in precisely because invented values cannot promise what a real install delivers — making that the default would turn "verify passed" into a guarantee it cannot keep, which is the failure being fixed. Three ergonomics changes ride along, all convention rather than format because every path is already vendor-named: a `yaml-language-server` modeline pointing at the JSON Schema 0004 already generates and publishes and that nothing points at, so editors give completion and would have caught the unquoted-`mode` trap; `.yaml.tmpl` on templates so an editor stops linting Go template syntax as YAML; and the secret schema out of `templates/`, where it never was one. Amended to carry `release new`, because §5.2–5.4 are retrofits for existing bundles and *defaults* for new ones: without a scaffold they stay documentation, and every bundle authored in the meantime needs the same retrofit by hand. The scaffold's output must pass `verify --render-check` unedited, which couples the two halves — neither the scaffold nor the verifier can move without the other. **Shipped 2026-08-09 without P4**: `--render-check` is unbuilt, so the scaffold is asserted against plain `verify` — the weaker gate §12 already allows for — and `--from-example` is unshipped, because embedding `testdata/bundle` needs a copy inside the module's embed root that would drift from the fixture whose maintenance is that option's whole justification. **Design locked 2026-08-08**: `--render-check` stays opt-in *permanently* rather than pending a maturity it cannot reach — a synthetic context invents its values however good it gets, so the guarantee never becomes real, and a future "it has proven itself, make it default" would recreate the exact failure the RFC exists to fix. |
| [0014](0014-building-a-release-bundle.md) | Building a release bundle | ✅ Complete | `morzer release build` and `release archive` — the two commands between a bundle source tree and something publishable, and two rather than one because the signature lives *inside* the archive, so signing has to sit between them and signing is the boundary the manager does not cross. Exists because archive entry order stopped being a convenience the day [0011](0011-bundled-container-images.md) decision 11 locked: the extraction budget is read from the tar stream, so `manifest.yaml` must arrive first — while `tar --zstd -C bundle .` emits directory order and [0012](0012-packing-images-into-a-bundle.md) §8 excluded archiving, leaving a locked decision resting on a step nothing owned. Locks the order as a property of the format, requires 0011's read to **fail closed** when it is not honoured, and takes the reproducibility requirement 0012 deferred to whoever owned that step. That fail-closed read shipped with 0011 P1 on 2026-08-09, alongside the budget read it guards: an archive whose first entry is not `manifest.yaml` is refused whatever it contains, because a fallback for the no-images case would make the ordering advisory. Also stamps the version, optionally from `git describe`, as `<next-patch>-dev.<distance>.g<sha>` — and three of that scheme's choices are forced by measurements against the pinned semver library rather than taste: a prerelease sorts *below* its own release (so the patch must be bumped, which is `setuptools-scm`'s `guess-next-dev` arrived at from the same constraint), build metadata is retained by `String()` yet ignored by `Compare()` (so metadata-differing builds land in different release directories that the never-republish check never compares — a silent bypass of the guard, closed by refusing `+metadata` in `metadata.version`), and OCI tag grammar excludes `+` (so the sha is a prerelease identifier). Refuses a dirty tree, and fails loudly rather than defaulting when no tag is reachable — the shallow-clone failure `actions/checkout` produces by default. **Design locked 2026-08-08**, and one refusal came out of reading the code rather than reasoning about it: `Version.IsZero()` tests `sv == nil`, so `0.0.0` parses, validates, sums, signs and installs like any release — and it is exactly what [0013](0013-bundle-authoring-experience.md)'s scaffold writes, which makes a forgotten `--version` collide on the *second* build rather than merely risk it, while `CheckUpgrade` only warns on a lower target. `build` refuses the null version and nothing else, so the sums-only path survives. |
| [0015](0015-notifications.md) | Notifications | ✅ Complete | `ports.Notifier` is a fully specified port with **zero implementations**: four operations call `d.notify(...)` and every call returns on the nil check, on every machine, so the port's careful "an update must not fail because a webhook was down" describes behaviour that has never run. Ships a webhook adapter configured exactly like [0009](0009-backup-targets.md)'s backup targets — a list of `{url, credentials}` with the credential named rather than embedded, so no token reaches the operator-facing file or `doctor` output. The motivating gap is sharper than the missing adapter: `backup` and `restore` have no notify call site at all, and `backup` is the *only* operation with a generated systemd timer — so the one thing that already runs with nobody watching is the one thing that cannot say so, and [0009](0009-backup-targets.md) made a failed push fail the whole backup precisely so success cannot mean "still only on the doomed machine", producing a correct, loud failure delivered to an empty room. What leaves the machine is an **allowlist**, not a denylist, so a `Kind` added later is not forwarded until someone classifies it; `step.output` never leaves, because it is raw vendor-controlled subprocess output and the "events carry no secrets" claim rests on a redaction handler [0008](0008-test-coverage-program.md) already caught leaking anything that was not a `string` or an `error`. Delivery is at-most-once by decision rather than omission, which binds [0016](0016-update-checking-and-unattended-updates.md): an unattended update may not treat "notified" as a precondition, and the journal stays the record. **Design locked 2026-08-08**: two URL forms, because a Slack-style webhook URL *is* a bearer token spelled as a path and a plain `url` field lands it in the operator-facing file, in `doctor` output, and in an `installation export` beside a recovery key — while an endpoint carrying no credential should not be forced into the secret store either; and `min_level` per target defaulting to `error`, which buys the warn-versus-error choice without the deduplication §8 excludes. |
| [0016](0016-update-checking-and-unattended-updates.md) | Update checking and unattended updates | 🚧 In progress | `ReleaseSource.List` has been implemented against the OCI tag list since [0004](0004-distribution-and-verification.md), carries a comment saying it exists for exactly this — "the one transport that *can* answer, which is why `List` is on the port at all" — and **has no callers**. Wires it up as `update --check`, then adds what a sandbox loop actually needs and `List` structurally cannot give it: following one mutable tag through `Resolve`, since `List` skips non-semver tags by design and a `dev` tag is therefore invisible to it. Mutable pointer, immutable versions — composes with [0014](0014-building-a-release-bundle.md), which gives every build a distinct version, so the never-republish refusal keeps working untouched. Unattended apply comes last and opt-in, gated not on a version range (a proxy, and a bad one in both directions — a patch can carry an emergency one-way migration) but on the release **declaring** that a failure will not need a database restore — narrower than "cannot require a human", which the gate cannot promise since a failed migration hook still stops and waits for a person: `rollback_safe: true` plus a schema range the previous release can still read, which is `AssessRollback` run predictively over data the manifest already carries. Refuses to enable at all without `require_signature` and a pinned key, because auto-apply hands the vendor unattended root; anything failing the gate is fetched, staged and notified rather than silently skipped, which is where most of the value sits with almost none of the risk. The timer is a sibling of the backup timer that already ships, `OnCalendar` *is* the maintenance window, and checking is off by default because it is a phone-home. **Design locked 2026-08-08**, with two answers that changed under inspection. The gate's schema half needed a real manifest field — `database_schema_produces`, absent meaning not auto-applicable — because the `database_schema_min` stand-in lets a release migrating past its own declared minimum through, and a gate whose argument is "declaration, not proxy" cannot use a proxy for half of itself; strict decoding then makes any new manifest field a hard break for older managers, which `min_manager_version` cannot soften because `CheckUpgrade` runs *after* the decode fails. And `mode` is immutable rather than one-way, since both transitions are dangerous in different shapes — which surfaced `installation import` as a second creation path and, with it, a hazard: an import keeps the original installation id and [0009](0009-backup-targets.md) puts backup targets *and their credentials* in the export, so `import --mode dev` must drop them or a sandbox pushes throwaway backups into the customer's bucket under a matching id. |

| [0017](0017-recovery-artifacts.md) | Recovery artifacts | 🚧 In progress | Recovering a machine takes three artifacts — a recovery key, an export and a backup — and only two of them are produced automatically. The one carrying identity is the manual command that nothing schedules, nothing reminds anyone to re-run, and no `doctor` check reports on, while the one every operator has cannot rebuild identity *despite already containing almost everything needed to*. `captureManagedComponents` writes five files that approximate an `InstallationExport`, and the most important is the wrong copy: it takes the operator-facing `installation.yaml` rather than the authoritative state, and this codebase already ships a `config.installation-file` diagnostic **because those two drift**. So a backup carries a copy of the installation that is documented as possibly wrong, in the artifact somebody reaches for during recovery. Has the backup carry a real export from the same code path (pinned by a byte-for-byte equivalence test, without which "one producer" decays quietly back into two), retires the `secrets` component as subsumed byte for byte — keeping it would put the secret state in one backup twice — and redesignates `config` as forensic rather than recoverable, which turns a trap into two labelled artifacts. Adds `installation import --from-backup`, needing no change to `Import`, which already takes a parsed export *value*; and a single-file fetch on the target port so importing identity from a bucket costs kilobytes rather than the whole archive — a small addition precisely because `List` already reads one named object per remote backup through the same helper. `installation export` survives and is reframed rather than removed: a release with no backup hook and no capturable volume is *refused* a backup by [0010](0010-compose-volume-capture.md), so some installations can never produce one. For an installation with a recovery recipient, recovery becomes **recovery key + any backup taken after this ships** — the qualification matters, because §5.4 refuses a backup carrying no export component, which includes every backup from an installation that never had a recovery recipient to encrypt one to. Three controls fall out of reviewing the risks: the export component is encrypted to the **recovery recipients only**, so it is unreadable by the machine that wrote it and compromising the live host yields the data but not the identity — and it is *skipped* rather than machine-encrypted when there is no recovery recipient, since an identity bundle readable only by the key that dies with the machine is the appearance of recovery with none of the substance; `--from-backup` with no id takes the **newest** export, decoupling identity from data so that restoring to a point in time does not silently recover that moment's secrets too; and `<PRODUCT>_BACKUP_DIR`'s contents are enumerated as an ABI in the same change that retires `secrets`, because after the first tag whatever vendors read becomes a contract whatever the docs say. One risk in the first draft was overstated and is corrected in place: the "captured nothing" refusal counts `capturedVolumes`, not components, so an always-present component cannot satisfy it. |

| [0018](0018-the-pre-1-0-manifest-surface.md) | The pre-1.0 manifest surface | ✅ Complete | A deliberate one-time sweep of the manifest before the first tag, run because decoding is strict and — verified by adding one key under `runtime:` — **recursive**, so there is no reserved area and no nesting trick: every field at every level freezes the moment a manifest exists that this project did not write. Two parts. A **two-pass decode**, because `min_manager_version` is read by `CheckUpgrade` on an *already-decoded* manifest, so the mechanism built to say "you need a newer manager" can never speak and an operator instead gets `unknown field` at line 22 about a file they did not write; a lenient preamble pass fixes the message. It does **not** make future fields free — an old manager still cannot install the release — and §5.1 bounds that claim deliberately, because overselling it is the main risk. And the fields that should exist before the freeze, each an **asymmetry rather than a feature**: `parameters.required` (a secret can be required, a parameter resolves silently to `""`), `requirements.cpus` (memory and disk are bounded, CPU is not), `metadata.release_notes` (every other path a bundle ships is declared and existence-checked, so `RELEASE.md` would be the lone convention — and [0002](0002-rich-terminal-renderer.md) P5 now depends on it), `health.checks[].start_period` (without it, slow-to-start and dead are the same observation), and `metadata.support_url` for a product whose operator is not its vendor. Gives [0011](0011-bundled-container-images.md)'s extraction budget the home it was locked without — `bundle.uncompressed_size`, because `requirements` describes the host and this describes the artifact. Six rejected fields are recorded with what reopens each, since an unrecorded rejection is re-proposed. Also corrects a misreading: `extensions` looks dead but exists to be *tolerated*, so a vendor's namespaced keys do not trip strict decoding — which incidentally makes it a real forward-compatible home for experimental manager fields. |
