# RFC 0036 — Generating a secret a new release declares

- **Status:** ✅ Complete — written and built 2026-10-29, in one PR with
  [#163](https://github.com/morzecrew/morzer/issues/163). Every decision is
  `ASSUMED`: none was ruled before the build, and each is open to the author's
  ruling in review. Gaps the build exposed are in
  [logs/rfc-0036-update-generates-secrets.md](../logs/rfc-0036-update-generates-secrets.md).
- **Scope:** What `update` does with a secret the release it installs adds:
  which secrets it generates, where in the pipeline, how an operator turns it
  off, what a plan says, what a failed update does with the value, and why
  `apply` and `rollback` do not do the same. Not removing a value no release
  declares any more, and not any change to how `init` or `secret generate`
  choose. One new step in `update`, one flag, no manifest change, no schema
  change, no port change.
- **Related:** [`internal/lifecycle/ops/update.go`](../internal/lifecycle/ops/update.go),

## 1. Summary

`update` gains a step, `generate-secrets`, before it converges. The step
generates each secret that the release being installed declares with a
generator, that has no value on this machine, and that the release being
replaced did not declare. It is `init`'s rule, applied to what the new release
adds. A plan names what it would generate. `--generate-secrets=false` turns it
off, as it does for `init`. A value generated by an update that then fails stays
in the encrypted state, and the retry finds it. `apply` and `rollback` generate
nothing.

## 2. Motivation

morzer generates secrets only in `init`'s `init-secrets` step. When release N+1
declares a secret N did not, every machine installed under N reaches N+1 with no
value for it (#163):

- **A required secret** stops the update at `load-secrets` with `required
  secret(s) not set: <name>`. On a machine following a channel, the timer fails
  the same way every tick, and the machine stays on N until somebody runs
  `morzer secret generate <name>`.
- **An optional secret** renders no file. A Compose `secrets:` entry whose
  `file:` is missing then fails at start, which is later and worse.

The vendor cannot say "generate this on upgrade". All the vendor can do is ask
in the release notes for a manual step, which an unattended machine never reads.
Adding a secret is an ordinary release, and `init` already knows how to make one.

## 3. Current state

- **`init`** (`stepInitSecrets`) loads the secret state and walks the release's
  schema. A declaration that already has a value is left alone. One with an
  automatic generator (`Generator.Auto()`) is generated, unless
  `--generate-secrets=false`. `required` plays no part in that choice. It only
  decides which unset names the closing warning lists.
- **`update`** runs four steps of its own, `stage-update`, `ingest-images`, then
  `applySteps` against the staged release. `apply` and `rollback` run
  `applySteps` too. `load-secrets` refuses a declared `required` secret with no
  value (`SecretSchema.Missing`), before anything is rendered or started.
- **`render-secrets`** renders one file per declaration with a value, and
  removes files no declaration backs (`pruneStale` in the sops-age adapter).
  When an update fails and is compensated, the previous release's secrets are
  rendered over the new ones, which prunes anything only the new release
  declared (`restorePreviousRuntime`).
- **`Update`** already reads the release it replaces before the operation
  starts, as `running`, to take the runtime baseline and to know what a failure
  falls back to (`fallbackRelease`). That read is allowed to fail when the
  baseline is recorded.
- **`SecretStore.Generate`** refuses to overwrite an existing value unless asked
  to. An unattended tick calls `Update` with the options the timer's command
  line gives it.

## 4. Goals / Non-goals

**Goals**

- A release that adds a secret with a generator installs on an existing machine
  with no manual step, unattended included.
- A required secret with no generator still stops the update at `load-secrets`,
  because only the operator can supply it.
- The generation is planned, visible, and never prints a value.

**Non-goals**

- Removing a value from the encrypted state when no release declares it. The
  render already removes its file. Whether `doctor` should list such values is a
  separate question (§8).
- Changing what `init` or `secret generate` do.

## 5. Design

### 5.1 Where it runs

One step, `generate-secrets`, in `update`'s own list, after `ingest-images` and
before the converge steps it shares with `apply` and `rollback`. That puts it
before `load-secrets`, so the value it writes is loaded, registered with the
redactor and rendered by the same run, and `load-secrets`' refusal still catches
a required secret that has no generator.

```text
verify-bundle, check-compatibility, pre-update-backup, restore-point,
stage-update, ingest-images, generate-secrets,
preflight, load-secrets, render-secrets, …
```

- **Idempotent, with a `Check`.** Generating is done when nothing is left to
  generate. A resumed or retried update finds what an earlier attempt wrote, and
  generates nothing twice. `Generate` refuses to overwrite in any case.
- **Aborts on failure, compensates nothing**, as `load-secrets` does. Nothing
  else has changed yet, and a value it did write is one the retry needs (§5.4).

`apply` and `rollback` do not generate. Each converges a release this machine
has already run: a secret that release declares had a value when it was
installed, or the operator chose to leave it unset (`init
--generate-secrets=false` warns that they are "still to be set before
`apply`"). A value that is missing now was removed, or never set, by a person.
Generating over that choice would turn a refusal that names the secret, with a
`secret generate` hint, into a deployment running on a random value nobody
chose. `restore` converges the installed release the same way, and `import`
brings its own secret state.

### 5.2 Which secrets

A secret is generated when all three hold:

1. the release being installed declares it with an automatic generator;
2. this machine has no value for it;
3. the release being replaced did not declare it.

The third clause is what keeps an operator's choice. A secret both releases
declare and this machine has no value for was left unset on purpose. Only an
optional one can be in that state on a running machine, because `load-secrets`
refuses a required one. That choice holds across the update.

`required` plays no part, as in `init`: an optional secret with a generator is
one the vendor expects to exist, and a missing file fails at start (§2).

When there is no replaced release (a first install through `update` on a
machine `init` created without one), every declared secret counts as new, which
is `init`'s own rule. The same holds when the replaced release cannot be read
(§3). Nothing can then be known about what it declared, and treating every
secret as new is the choice that lets the update proceed.

### 5.3 Turning it off

`update --generate-secrets=false`, the flag `init` already takes and with the
same meaning. The step then generates nothing. A new required secret stops the
update at `load-secrets` as it does today, and the operator sets it from outside
and retries. The choice is journaled as the operation flag `generate_secrets:
false`, beside `skip_backup`.

There is no per-installation setting. An unattended tick takes the default and
generates. That is the case #163 exists for, and generating never replaces a
value the operator set.

### 5.4 Plans, reports and failures

- **A plan** runs the step's `Check`, which reads the secret state, and names
  the secrets in the step's line: `generate secrets the release adds — would
  generate webhook_key`. It writes nothing. A plan that cannot read the secret
  state says it cannot determine, as other checks do.
- **A run** says what it generated in the step's detail: `generated 1 secret
  1.3.0 adds: webhook_key`. The value is never printed, logged or journaled. The
  journal records the step as run or skipped. The names are on the terminal and
  in the `--json` event stream, and each value's metadata says when it was set.
- **A failed update** leaves the generated value in the encrypted state. The
  previous release does not declare it, so rendering that release on the way
  back removes its file. The next attempt finds the value and generates nothing.
  Removing the value on compensation would only make the retry generate a
  different one.

### 5.5 Manifests and older managers

No manifest field and no compatibility gate. A release that adds a secret
behaves on an older manager as it does today: the update stops at
`load-secrets`, or at start. A vendor who relies on the generation can raise
`compatibility.min_manager_version` themselves. The manager does not require it.

### Alternatives considered

- **Generate every missing secret with a generator, in `applySteps`.** This is
  what the issue first suggests, and it is `init`'s rule applied everywhere. It
  would give `apply`, `update` and `rollback` one step and one rule, but it
  overrides `init --generate-secrets=false` at the next `apply`. An optional
  secret left unset on purpose would also be filled at every converge. The
  third clause of §5.2 costs one read of the replaced release, which `Update`
  already does.
- **Generate in `load-secrets`.** That step only reads, and its whole job is to
  fail before anything is written. A plan would also not show the generation.
- **A manifest field marking which secrets an update may generate.** A
  generator already says the vendor accepts a random value. A second field
  would say it twice, and an older manager would refuse the bundle for it.

## 6. Tests

`test/suite` against the update harness and a 1.3.0 bundle whose schema adds a
secret:

- an update generates the added secret, renders it, names it in the step, and
  leaves its value out of the journal;
- a secret both releases declare and the machine has no value for is not
  generated;
- a required secret the new release adds with no generator still stops the
  update at `load-secrets`;
- a plan names the secret and generates nothing;
- `--generate-secrets=false` (`NoGenerateSecrets`) generates nothing and is
  journaled;
- a failed, compensated update keeps the generated value and removes its file,
  and the retry keeps the same value.

The flag's wiring is covered in `test/clitest`.

## 7. Docs

The `update` reference gains the step and the flag. The secret schema's
reference and the first-bundle guide say when a secret is generated: at `init`,
and at an update whose release adds it.

## 8. Out of scope

- **Values no release declares.** The render removes their files, and the values
  stay in the encrypted state, which is what a rollback needs. Nothing reports
  or removes them. Whether `doctor` should list them is left open, as #163
  leaves it.
- **A per-installation opt-out.** The flag is per run. An installation that
  never wants generation would need a recorded choice, which is a schema change
  with no request behind it yet.

## 9. Risks

- **A vendor adds a generator to a secret that must match something outside the
  machine.** The update then generates a value that does not match. That was
  already true at `init`, and the generator is the vendor's statement that a
  random value is acceptable.
- **A replaced release that cannot be read** makes every missing secret with a
  generator count as new (§5.2). That can fill an optional secret the operator
  left unset. Accepted: the alternative is an update that cannot proceed on a
  machine already in an unusual state.

## 10. Unresolved questions

None the build depends on. Whether `doctor` lists values no release declares
stays open (§8).

| 2 | `ASSUMED` | It generates a secret the new release declares with an automatic generator, that has no value here, and that the replaced release did not declare. With no replaced release, or one that cannot be read, every declared secret counts as new (§5.2). |
| 3 | `ASSUMED` | `required` plays no part in the choice, as in `init`. |
| 4 | `ASSUMED` | `apply` and `rollback` generate nothing: they converge a release this machine has run, and a missing value there was left unset or removed by a person. `restore` and `import` generate nothing either (§5.1). |
| 5 | `ASSUMED` | `update --generate-secrets=false` turns it off, as for `init`, and is journaled as the flag `generate_secrets: false`. There is no per-installation setting (§5.3). |

| 7 | `ASSUMED` | A plan names the secrets the step would generate and writes nothing (§5.4). |
